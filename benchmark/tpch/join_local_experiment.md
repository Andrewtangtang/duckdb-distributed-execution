# Q19 join partition experiment (local ObjFS)

Branch: `experiment/partitioned-join-q19`. The driver partitions the larger native table of a two-table inner join by row group. Each worker runs the full join against the other table and returns a partial aggregate; the driver merges the partial values. The path is limited to queries supported by the existing partial aggregate rewriter and runs only in autocommit mode. Unsupported plans retain local execution.

## Setup and measurement

- DuckDB 1.5.6 release build on one macOS machine, local ObjFS, Q19 from `tpch_queries()`. The SF1 and SF10 databases were generated by TPC-H `dbgen`, then `lineitem` and `part` were copied into separate local ObjFS databases with row groups of 122,880 rows.
- Compare the same binary with a driver started with zero workers against a driver started with three local workers. Each process runs Q19 three times. Times below are server `query_duration_ms`; the first run includes process and cache effects, and the next two use warmer caches. These are exploratory measurements, not a controlled S3 benchmark.
- SF1 has 6,001,215 `lineitem` rows and 200,000 `part` rows. SF10 has 59,986,052 and 2,000,000 respectively.

| Scale | Workers | First (ms) | Warm 1 (ms) | Warm 2 (ms) | Q19 revenue |
| --- | ---: | ---: | ---: | ---: | ---: |
| SF1 | 0 | 68 | 19 | 14 | 3083843.0578 |
| SF1 | 3 | 102 | 25 | 24 | 3083843.0578 |
| SF10 | 0 | 323 | 174 | 151 | 30104438.0911 |
| SF10 | 3 | 606 | 221 | 215 | 30104438.0911 |

The query history recorded `ROW_GROUP_PARTITION`, `AGGREGATE`, three workers, and three tasks for each distributed run. In a second SF10 pass with local execution first and then distributed execution, alternating each three-query batch, the median of four warm runs was 126.5 ms local and 185 ms distributed. The local ObjFS runs did not improve Q19 latency. Re-reading `part` on each worker, planning/dispatch, and result transfer add work while DuckDB already parallelizes the local query. The earlier S3 latency benchmark may have a different crossover point; this experiment does not establish one.

## Verification

`unittest_duckherder '[task_partitioner],[partial_aggregate],[query_utils]'` passed: 7 test cases and 213 assertions. The join test checks three generated tasks, deleted rowid gaps, multiple `OR` filters including one without a safe implied dimension predicate, exact merged SUM, and outer join fallback. The Flight integration suite also passed: 19 test cases and 178 assertions. The end-to-end SF1 and SF10 runs returned the same revenue in both modes.

## Reproduce

Build `unittest_duckherder`, `distributed_server`, and `duckdb` in this worktree. To create SF10 data, run `CALL dbgen(sf=10)` in a local DuckDB file, then copy `part` and `lineitem` into a `duckdb_objfs://tpch.db` database with `ROW_GROUP_SIZE 122880` and the local ObjFS backend. Start one driver with `distributed_server 127.0.0.1 18875 3` and another with `distributed_server 127.0.0.1 18876 0`. Attach each from the DuckDB shell using `TYPE duckherder, READ_ONLY, DATA_PATH '<objfs root>'`, run `PRAGMA tpch(19)` three times, and inspect `duckherder_get_query_execution_stats()`.

Before enabling this path by default, benchmark against S3 at the original SF10 network latency and add a cost gate based on scan size, dimension size, and storage latency. A hash shuffle remains necessary for joins where neither side is economical to replicate.

## Where the time goes

The path is client Flight `DoGet` → driver SQL plan and row-group partitioning → parallel worker Flight `DoGet` → each worker runs DuckDB SQL and converts its result to Arrow → driver merges partial aggregates → client Arrow result. `DUCKHERDER_PROFILE_DISTRIBUTED=1` prints driver, RPC, worker, and row-group timings. `DUCKHERDER_WORKER_PROFILE_DIR=<directory>` additionally writes DuckDB JSON operator profiles for each worker task.

For three local workers on warm SF10 data, before the predicate rewrite:

| Stage | Observed time |
| --- | ---: |
| Driver parse, plan, and aggregation analysis | 0.4–0.6 ms |
| Row-group partitioning | 0.2–0.3 ms |
| Result schema preparation | 0.7–0.8 ms |
| Dispatch, worker execution, result transfer | 165–175 ms with default threads; 137–140 ms with four threads per worker |
| Driver partial aggregate merge | 0.5–0.6 ms |
| Worker query itself | 163–174 ms with default threads; 130–138 ms with four threads per worker |
| Worker database lookup, session setup, Arrow conversion | Under 0.3 ms combined on warm runs |

The old worker `DoAction` only acknowledged a task; `DoGet` actually ran it. That extra Flight round trip took roughly 0.2–1 ms per task on warm runs. Removing it simplified dispatch, while worker SQL still dominates latency. Worker Arrow fetching and driver merge are also small for Q19's one-row partial results. Both sides currently materialize Arrow batches, so large result sets need a separate measurement before drawing the same conclusion.

Row-group pruning is working: three workers each scanned 163–164 of the 491 `lineitem` groups. Each worker nevertheless read all 2 million `part` rows and built a hash join. With four DuckDB threads per worker, a representative worker profile showed about 134 ms wall time and 477 ms summed CPU time. The `lineitem` scan used about 187 ms CPU, hash join 165 ms, and post-join filter 55 ms. Operator CPU times sum across threads and must not be added to wall time.

On a first run after worker startup, opening the ObjFS database took about 13–18 ms per worker while worker SQL took more than 620 ms. Initial storage reads, rather than database attachment or RPC, dominated that run too; cold timings varied substantially with the shared OS cache.

## Changes tested

The branch now extracts an equality on the same dimension column from **every** branch of a top-level OR of conjunctions. It adds their OR as a redundant, implied `WHERE` condition to worker SQL. It only accepts direct column-to-constant equality and unambiguous column ownership, so the added filter cannot remove a row satisfying the original condition. For Q19, this produces a `part.p_brand` filter before the join.

In the representative worker profile, the dimension filter reduced post-join rows from about 716,000 to 86,000; hash join CPU time fell from about 165 to 15 ms and the post-join filter from about 55 to 2 ms. Worker summed CPU time fell from about 477 to 253 ms. The query still returns `30104438.0911` at SF10. Three workers with four threads each went from about 138–148 ms to 77–82 ms warm. The same query with default ten threads per worker was about 84–89 ms after the rewrite, so the filter accounts for most of the gain.

Local worker startup now budgets DuckDB threads across workers: `ceil(hardware_concurrency / local_worker_count)`. On this ten-thread machine, three workers get four threads each. One or two threads per worker were slower, and four workers with three threads each were about 83–84 ms warm on this query. Standalone workers retain DuckDB's default setting.

The fair comparison matters: a local DuckDB query with the *same* implied `p_brand` filter took about 62–66 ms warm, compared with about 109–122 ms for the original local SQL. Thus the semantic filter rewrite improves both modes; the distributed path itself is still slower than an equally optimized single-node query on local ObjFS. The earlier 77–82 ms versus 109–122 ms comparison should not be read as an intrinsic distributed speedup.

Next, share the safe predicate rewrite with the local planner or upstream DuckDB, then add a cost gate using storage latency, fact size, and replicated dimension size. For S3, measure the same Q19 path before deciding whether to distribute. For joins whose dimension is too large to replicate, use a hash shuffle. For joins with large outputs, profile Arrow materialization and merge separately; Q19 does not exercise those costs.
